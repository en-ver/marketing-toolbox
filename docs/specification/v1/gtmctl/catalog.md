# `gtmctl` v1 API catalog

## Status

This is the complete, contract-first target catalog for the official Google Tag
Manager API **v2**. It was derived from the official Google Discovery document
(snapshot: [`upstream-inventory.json`](upstream-inventory.json); retrieved
2026-07-25). The current local checkout implements the complete v1 `gtmctl`
interface described here; this is not a claim about a remote branch, merge, or release.

The Discovery document contains **106** methods: **104 implemented stable
targets** and **2 excluded deprecated methods**. The excluded methods must not
be exposed by `gtmctl` v1.

## Source and SDK boundary

- Authoritative upstream inventory: Google Tag Manager API v2 Discovery
  document, `https://www.googleapis.com/discovery/v1/apis/tagmanager/v2/rest`.
- Python adapter: `googleapiclient.discovery.build("tagmanager", "v2")`; the
  catalog's adapter column identifies the dynamic resource/method chain to call
  before `.execute()`.
- The target CLI hierarchy mirrors the official resource hierarchy. Its 104
  stable targets are implemented locally; the two deprecated destination
  methods remain intentionally excluded.
- Only methods labelled `stable-target` can become v1 Google-operation
  commands. The catalog is the Google-operation allowlist. The separate
  local-only `gtmctl sdk schema` descriptor tool is not an upstream method and
  is specified in [the SDK-backed introspection specification](../sdk-backed-introspection.md).

## Common command contract

### Identifiers and bodies

- Each official required `path`/`parent` parameter is a required kebab-case CLI
  option (for example, official `parent` becomes `--parent`). Its value must be
  passed unchanged to the official request; implementations may validate the
  canonical GTM resource path but must not invent substitute identifiers.
- A method whose official request resource is required exposes required
  `--body <file|->`; an optional official request resource exposes optional
  `--body <file|->`. It is a bounded UTF-8 JSON object from a file or standard
  input and, when supplied, is passed as the official API request resource.
  `gtmctl` must not expose a locally
  authored `--schema` endpoint or catalog as an API surface.
- Every optional official query parameter is an optional kebab-case CLI option.
  The implementation must preserve the official field name in the HTTP request
  and must not add pagination knobs not offered by the method.
- List methods with `pageToken` return exactly one official response page and
  expose the returned `nextPageToken`; there is no hidden pager iteration.
- GET/read calls do not require `--dry-run` or `--apply`. All other stable
  actions use exactly one of `--dry-run` or `--apply`; dry-run builds and emits
  the official request without credentials or network traffic.

### Output, errors, and concurrency

- Successful commands write one `marketing-tools/v1` JSON envelope to stdout.
  `data` is the direct official JSON response. An empty successful response is
  represented as `{}`. No derived state or synthetic API data is emitted.
- Failures write one redacted normalized diagnostic to stderr and use the
  repository's established nonzero exit-code contract.
- No automatic retries, no automatic reconciliation, and no automatic
  pagination. `fingerprint` is passed only when explicitly supplied; it is the
  official optimistic-concurrency token and must not be fabricated.

### Safety

- **Mutation:** `--dry-run`/`--apply`; preserve resource fingerprints and
  report a dispatch failure as an unknown outcome.
- **Destructive:** mutation controls plus explicit destructive acknowledgement
  naming the irreversible class (container, workspace, entity, or version).
- **Publish:** mutation controls plus `--acknowledge-publish`; publishing must
  never be inferred from a write command.
- **Sensitive permission:** mutations use mutation controls plus
  `--acknowledge-permission-change`; permission reads require
  `--acknowledge-sensitive-data`. Never log or silently broaden grants.
- **High-impact:** mutation controls plus an operation-specific acknowledgement
  for account updates, bulk workspace changes, or environment reauthorization.
- These are CLI operational controls, not additional API methods. Exact
  acknowledgement wording and resource-specific redaction are specified in
  command-family contracts before implementation.

## OAuth scopes

The discovery document exposes these scopes: `tagmanager.readonly`,
`tagmanager.edit.containers`, `tagmanager.delete.containers`,
`tagmanager.edit.containerversions`, `tagmanager.publish`,
`tagmanager.manage.users`, and `tagmanager.manage.accounts`. Each command must
request one of the scopes listed for its official method; it must not default to
an unnecessarily broad scope.

## Delivery order

1. **Foundation and read-only discovery:** authentication, envelope/error
   handling, `accounts` and container/workspace/entity `get`/`list` commands,
   one-page pagination, and exact help/catalog tests.
2. **Ordinary workspace edits:** create/update/revert operations for workspaces
   and entities, with body passthrough, `fingerprint`, and dry-run/apply tests.
3. **Versioning and environments:** version creation/update/undelete/set-latest,
   quick preview, environment management, and explicit versioning scopes.
4. **High-impact operations:** deletes, user permissions, container moves and
   combine, gallery import, reauthorization, and publish only after their
   acknowledgement/redaction contracts are approved.

No implementation work begins until this catalog and the detailed
command-family contracts below are reviewed and accepted.
